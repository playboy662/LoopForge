# 平台通用工程约束

适用于所有平台共享角色。根据已有工程约定和 PZH 规范中的共性要求提炼；
具体任务中的用户指令和目标项目明确的约束优先，上游技能示例不能覆盖这些要求。

## 范围与决策

1. 先确认实际产品根目录，阅读项目 AGENTS.md、构建入口、当前 Git 状态和相似实现，再建模和实施。只访问、修改任务授权的仓库与目录；需要跨目录或跨仓库时先确认已有授权。
2. 先明确目标、范围、边界条件、验收标准、依赖与风险。优先复用项目基础库、组件和已有模式，保持最小必要改动，不把单个业务项目的框架、服务清单或个人机器路径写成全平台要求。
3. 角色各自完成约定职责；通过平台提供的协作入口交接，不另装第二套全局角色、Hooks、记忆或派工框架。流程、人工批准和任务权限由 LoopForge 管理。
4. 技术栈、依赖版本、构建命令和环境参数以目标项目及批准的变更为准。后端与前端规范中的技术栈条件只有在项目明确匹配时生效；没有匹配证据时使用通用条款。

## 契约与交付

1. 修改前明确接口、数据、配置和调用方的兼容性影响。共享模型、基础库和公共组件的变更必须检查相关使用方，不能只验证当前文件能编译。
2. 事实、假设、阻塞和待确认项分开说明。引用资料需要可核对依据；不得编造需求、接口、市场数据、测试结果或验收结论。
3. 复用项目的鉴权、请求、异常、日志和配置能力，保护密钥与隐私，不将凭据、内部部署地址或用户数据放进公共资产、日志或提交。
4. 交付内容与任务规模相称。简单修改不强制产出整套文档；正式产物和路径遵循任务约定，报告已完成事项、实际证据、已知限制和交接事项。

## Git、验证与清理

1. 遵循项目分支和目标合并分支约定；每个仓库独立记录改动范围、分支和提交。保护已有未提交内容，不擅自回退他人改动。
2. 提交说明必填，使用中文，详细说明改动范围、原因和验证结果。新增类文件默认执行 git add，用户明确要求不暂存时除外。未经授权不自动提交、推送、合并或部署。
3. 代码修改后执行项目约定的编译、安装或构建验证，并按变更风险执行适当测试。使用用户提供的编译入口和参数；技能里的 npm 命令、测试方法和覆盖率数字仅是示例，不能强加给所有项目。
4. 记录真实命令、退出码、结果和未验证范围。失败时继续定位，区分本次改动问题、项目原有问题和环境阻塞，不靠删测试、降门槛或自述“已通过”完成交付。
5. 仅清理本次产生或显著增长的临时工程、编译目录和一次性安装产物，保留正式交付物及持续运行所需依赖。不得清理用户无关的长期缓存。

## 技能选择与引用

1. 同一能力优先使用已安装的一份技能；按任务、技术栈和角色职责选择，不因技能可见就全部执行。`frontend-patterns` 适用于 React/Next.js，`backend-patterns` 适用于 Node.js/Express/Next.js API；Go、Java/Spring、Python、PostgreSQL 和 MySQL 分别按目标项目启用。
2. 上游正文中的技能前缀只是来源名称。读取或调用时使用平台实际技能标识：`superpowers:test-driven-development` 对应 `test-driven-development`，`superpowers:verification-before-completion` 对应 `verification-before-completion`。不要为前缀另装一份同义技能；其他未安装引用先确认用途和依赖，不能假定存在。
3. `verification-before-completion` 用于完成声明前核对证据；`verification-loop` 用于按任务选择构建、检查、测试和差异复核步骤。二者复用同一批有效证据，不重复执行相同验证，不把本地通过等同目标环境已验收。纯文档、配置或低影响修改使用与变更相称的验证。
4. `frontend-design` 必须先沿用已有设计系统和真实产品简报。信息不足时明确假设或澄清，不编造产品事实，不默认重做视觉。UI 设计师交付设计和交接说明；正式前端实现由任务指定的开发角色负责。
5. `technical-writing` 先使用现有文档体系与真实实现；模板中的文档站、脚手架、依赖安装和发布步骤只在任务需要且已授权时执行。`mysql` 仅用于 MySQL，遵循项目数据库版本与 DDL 规范；提供技能不代表已经提供 mysql CLI、连接信息或真实数据库变更授权。
6. 技能包内的命令、路径、工具清单和编排示例是待核对的参考，不能据此扩大目录、权限或任务范围。只使用平台现有协作入口，不因技能要求另起一套子代理、自动提交或流程系统。

## 浏览器自动化与产品交互验收

1. 有页面行为变更或任务要求交互验收时，先确定目标地址、构建版本、账号角色、测试数据、关键用户流程与预期结果。根据变更风险选择正常、异常和恢复路径；只读配置任务不因此启动整套产品测试。
2. LoopForge 的运行浏览器启动成功后会自动提供 `agentflow-browser`（Playwright MCP），无需在角色外部 MCP 清单中重复配置。交互验证优先使用它，让测试与用户看到同一个浏览器。先确认实际工具可用并能打开目标页面；浏览器未就绪时定位运行环境问题，将受影响场景标为阻塞或未验证，不能继续宣称验收通过。
3. `webapp-testing` 用于真实网页操作、状态核对、截图和日志；`e2e-testing` 用于项目内可重复执行的回归脚本与测试产物。复用已有框架和服务器。上游的 `chromium.launch()`、Python Playwright 安装、固定端口和 `/mnt/user-data/outputs` 仅是示例，不据此另装浏览器或把个人路径带入任务。独立 CI 测试进程按项目已有测试入口运行。
4. 从当前页面快照发现元素，执行点击、输入、选择、提交等操作，等待相关响应或可见状态，再断言最终结果。轮询或长连接页面不强制等待 `networkidle`，不靠固定休眠判断完成。数据保存后按场景重新打开或刷新核对持久状态；不得通过直接调用写 API、修改 DOM 或数据库来替代用户操作路径。
5. 测试角色负责功能自动化与回归证据；产品角色对照需求核对用户目标、关键路径与验收标准；UI 角色核对导航、反馈、设计一致性、响应式和基本可访问性。`steve-krug-ux-audit` 提供可用性走查方法；仅有截图时只能评审可见内容，不能推断行为通过。自动化通过与产品/UI 验收分别给结论；同一条证据可以复用，不必重复操作。
6. 涉及登录和权限时，按实际账号角色验证登录、退出、登录失效、无权限入口和拒绝提示。表单、弹窗、筛选、分页、加载、空态、错误、取消与重复提交按本次范围覆盖。桌面、移动端及键盘场景按产品支持范围选择；专业无障碍认证和性能指标必须有相应工具与实测，不能从截图推断。
7. 每个关键场景记录验收项、账号角色和前置条件、操作步骤、预期与实际结果、通过/失败/阻塞/未验证状态及证据路径。记录目标环境与版本；脚本回归另附运行命令、退出码和报告。截图、控制台与相关请求证据保存在任务规定的位置，运行浏览器默认使用 `.agentflow/browser/`；报告隐去凭据和敏感数据。
8. UI 走查默认只评审，不在验收过程中修改代码或伪造状态掩盖缺陷。修复后重跑失败场景及相关回归；没有执行的路径明确列为未验证。批量清理、真实支付、消息发送、权限调整与生产数据写入按任务授权执行，不因“测试”获得额外权限。
