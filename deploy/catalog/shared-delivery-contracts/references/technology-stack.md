# 项目技术栈与选型说明

适用于 Git/v2/v4 和 workspace_v1。技术方案正文必须单列「技术栈与选型依据」；本说明规定应说明的内容，具体选型由项目约束和批准方案决定。

## 说明的位置

- 项目配置的说明保存便于查找的技术基线摘要；详细约束可放项目绑定规则及仓库工程文档。
- 技术方案说明本次实际采用的组件、版本、目录、选择依据和验证方式，正式方案人审检查这一节。
- 共享 Skills 提供匹配技术栈的开发和验证方法；角色定义只约定专业职责，不指定所有项目必须使用同一框架。
- 构建环境资产说明有哪些工具；工具已经安装不代表业务必须采用，也不能证明应用实际使用该版本。

## 技术方案必需内容

| 方面 | 必须写清 |
| --- | --- |
| 前端 | 语言及版本、框架及版本、路由、状态管理、UI/组件/样式方案、构建工具与包管理器、浏览器及移动端范围。采用原生 HTML/CSS/JavaScript 时直接说明，不暗示存在 Vue 或 React。无前端时给出原因。 |
| 后端 | 语言与运行时版本、Web 框架或原生 HTTP 方式、模块分层、输入校验、认证与授权、数据访问及事务方式、依赖管理和构建工具。无独立后端时说明实际承担接口与持久化的组件。 |
| 数据 | 数据库引擎及版本、迁移工具、隔离及持久化方式；缓存、搜索、消息组件仅在实际采用时列明。数据库客户端版本和数据库服务端版本分别记录。 |
| 测试 | 单测、接口/数据库集成、浏览器交互采用的工具及版本，批准的独立构建/测试命令、适用测试数据与运行环境。 |
| 交付 | 部署形态、构建/运行镜像基底、服务与端口关系、静态资源与 API 路径、健康/版本接口以及环境资产引用。凭据只写引用。 |
| 依据与限制 | 继承现有工程还是本次新选型、满足哪些需求、版本兼容依据、主要代价和已知限制。区分设计目标版本、实际可用工具版本和已执行验证。 |

每项标注实际服务或应用目录。已有工程优先读取构建文件、锁文件和项目约束，以实际依赖为依据；新项目先核对用户指定及可用环境，再作出与场景相符的选择。不要把「最新稳定版」当作可复现版本，也不要照抄技能中的版本。

## 交接与维护

方案正文可使用以下表格，不新增或替换现有门禁要求的 JSON 字段：

| 服务/目录 | 组件与确定版本 | 用途 | 选型依据/来源 | 验证命令及结果或待办 |
| --- | --- | --- | --- | --- |
| 本次实际服务 | 语言、框架、数据与工具 | 本次职责 | 用户约束、现有工程或方案选择 | 实际结果；未执行须明确登记 |

前端与后端分别列项，详细设计继续使用当前协议。仅安装成功不能写成业务构建通过；尚未执行的验证保留待办。开发交付时核对实现依赖与批准选型一致，记录实际版本和适用差异；需要改变已批准技术栈时按 SOP 重新决策。

已有冻结方案不因补充本说明而重新生成摘要或修改批准文件。补充项目配置摘要时引用原批准版本，事实变化须经对应阶段重新确认。
