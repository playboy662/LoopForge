## 定义的组织方式

每份任务书包含专业目标、输入依据、职责范围、交付与质量要求、职责边界，并附加共同的阶段与交接约束。职责摘要仍为一段话，供列表和流程卡片展示；完整分工写入真正参与执行的 `prompt`。

角色不固化某个项目的地址、分支、凭据、框架版本或文件路径。具体方法与示例由 Skills 提供，执行顺序与审批由 SOP 管理；项目配置提供真实环境与仓库绑定。结构化产物须遵守当前阶段的字段、类型和标识，角色不得自行改名或更改冻结资料来绕过门禁。

## 应用与核对

1. 按 JSON 中的角色 ID 读取平台现有完整定义；该文件是文本字段更新补丁，不是替换全部角色属性的创建载荷。
2. 仅将 `description` 替换为补丁内容，将 `prompt` 设置为角色正文、两个换行及 `commonPrompt`，并基于当前版本递增一次版本号。
3. 保存前确认角色未被并发修改；角色缺失时先报告，不从该补丁创建缺少能力绑定的新角色。
4. 保留模型、思考强度、CLI、规则、Skills、MCP、循环、门禁、产物及人工确认设置。演示项目与其他角色不在本次范围内。
5. 保存后从 API 读回，逐字段核对正文和上述保留属性，并在 Orca 浏览器确认摘要和任务书展示。该操作不等于真实流程运行已通过，不自动重启需求。

重点保留：专业设计与实现的阶段边界、独立评审约束、真实版本和证据要求、缺陷与环境阻塞区分，以及当前 SOP 产物契约优先的原则。原先需求列表状态显示和方案门禁字段问题不属于此次修改，也未在此宣称修复。
